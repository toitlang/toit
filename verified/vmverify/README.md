# The format-2 verifier in the VM

Untrusted programs are verified by the structural verifier of format 2
(verified/spec: `v2::check::verify`, proven to decide `split_ok`, the
per-method form of the specification's `accepts`; `theorem_soundness_split`
in `v2/split.rs`) before any of their bytecode runs. This crate runs that
verifier inside the VM, on the program **as the VM will execute it**: the
abstract program is the tables the verified core gets, borrowed in place,
not a second parse of the snapshot bytes. Its memory is bounded by the
largest method plus small per-method tables, not by the program (see
"Memory").

## One Rust library

The VM links one Rust static library: this crate (`toit_vmverify`,
`crate-type = staticlib`). It depends on the core (`toit_verified_core`,
as an rlib) and on the spec crate, so the core's C entry points
(`toit_v2_run`, ...) and the verifier's are in the same archive with one
copy of Rust's std. Two Rust staticlibs in one binary each bundle std and
the Rust runtime symbols (duplicate definitions, two allocators, two
panic runtimes); a combined crate avoids that and leaves the core's own
crate untouched. verified/CMakeLists.txt builds this crate where it built
the core before (the CMake target keeps its name, `toit_verified_core`).

The profile is `panic = "unwind"` (the core alone uses `abort`): the
inference runs on untrusted input, and a panic must reject the program,
not abort the VM (`ffi.rs` wraps the verification in `catch_unwind` on
hosts). The inference is now total (PHASE4-REQUESTS.md R6: bounds-checked
everywhere, verified functions called within their preconditions, fuzzed;
see "Fuzzing"), and the verified checker cannot panic on indexing or
arithmetic (Verus proves it). `catch_unwind` stays anyway: the inference
(about 750 lines) and the conversion are plain Rust whose panic freedom is
argued and tested, not proven, and on hosts the catch costs nothing
measurable (the core's handlers do not unwind; benchmarks of richards,
deltablue, pystone in format 2 were within noise of the `abort` build,
-13 % to +5 %). Without `std` (devices) there is no unwinding: a panic
aborts.

## The C ABI (src/verifier_v2.h)

```c
uword toit_vmverify_verify(const toit_vmverify_input* input, toit_vmverify_result* result);
```

- `input->program` is a `toit_v2_program` (src/interpreter_v2.h), the
  struct `Interpreter::run_v2` hands to `toit_v2_run`, filled by the same
  C++ function `v2_program_tables`: bytecodes, the decoded method table
  (`V2Method[]`), dispatch table, class bits, class-check ids, interface
  check offsets, invoke offsets, entry points, builtin class ids, roots,
  literals, the program image range, the global max height. For
  verification the globals are the program's initial values
  (`program->global_variables`; a process' globals start as a copy).
- `input->prim_counts/prim_arities`: the VM's primitive table, generated by
  the C++ compiler from the `MODULES` declarations in src/primitive.h (the
  ones the primitives are compiled from). The layout check compares the
  verifier's generated table (`v2/prim_arity.rs`, used by the dump path)
  with it.
- `input->trusted`: the rules (untrusted launches pass 0: HALT 2 and 3
  are rejected).
- `input->certificate/certificate_length`: the shipped certificate
  (verified/spec/format/18-shipped-certificate.md) or null. With one, the
  proven `cert::verify_shipped` decides alone; without one, hosts (cargo
  feature `infer`, the default) infer the certificate, devices (built
  without `infer`) reject with `NO_CERTIFICATE`.
- Result: `code` (`ACCEPTED`, `MALFORMED` memory not convertible, `HEAP`
  loader contract, `TABLES` `wf_program2`/`tables_ok`, `METHOD` with
  `method` and `offset`, `INTERNAL` verifier panic, `CERTIFICATE` shipped
  certificate malformed or rejected, `NO_CERTIFICATE`), a message naming the
  reason and the instruction (`BRANCH_IF_FALSE 0 0: ...`), the number of
  program-heap objects, the time of each phase and the Rust heap
  high-water mark.

`V2Verifier::verify` (src/verifier_v2.cc) calls it and prints the reason;
`TOIT_VERIFY_TIME=1` prints the cost. `toit_vmverify_canonical` writes the
canonical form of the converted program (test support).
`toit_vmverify_certify` (hosts, `infer`) is the toolchain's producer:
it infers the certificate, checks it with `verify_shipped`, and returns
its bytes (`toit.run --certify`, which toit.compile runs).

## Where it runs

Every untrusted launch, before any bytecode runs:

- `snapshot.launch` (src/resources/primitive_snapshot.cc) and
  `programs_registry.spawn` (src/primitive_programs_registry.cc; this is
  also `toit run --untrusted`, which starts the program as an untrusted
  container) decode the method table once (`V2MethodTable::compute`), call
  `Verifier::verify_for_policy` with it, and hand that table to
  `ProcessGroup::create`. A rejected program is refused with
  `VERIFICATION_FAILED`.
- `ProcessGroup::create` verifies an untrusted format-2 program itself if
  it gets no table (no other path creates untrusted groups today; this
  keeps it so).
- Install-time verification (Phase 5, every platform): an image flagged
  untrusted (`ContainerService.FLAG-UNTRUSTED`, metadata byte 0 bit 2) is
  verified with the untrusted rules when it is committed to the flash
  registry (`image.writer-commit` and `flash_registry.allocate` call
  `V2Verifier::install_verdict` after the last byte is written, before the
  header). A rejected image is not committed (`VERIFICATION_FAILED`). An
  accepted one gets the verdict, metadata byte 0 bit 6
  (`FlashAllocation::Header::FLAGS_PROGRAM_VERIFIED_MASK`, only the VM
  sets it), and the header checksum of such an allocation covers the
  program's bytes too (the whole allocation without assets), so the
  verdict is bound to the bytes it was computed on: any change makes the
  allocation invalid (it is no longer listed and cannot start). Spawn
  takes the verdict instead of verifying (`V2Verifier::accept_recorded`
  marks the table it decodes from those bytes) and refuses a flagged
  format-2 image without one. Cost of the binding: a CRC-32 of the image
  on each lookup of the allocation (`FlashAllocation::is_valid`; Utils'
  nibble-table CRC, about 1 ms per 60 KB on the host, estimated several
  ms on an ESP32-C6). Test: tests/sandbox/install-verdict-test.toit
  (installs, checks the verdict, starts it from flash in a second VM
  without verification, corrupts a string of the program in the flash
  file, checks it no longer starts, and checks that a rejected program is
  not installed; 64-bit and 32-bit hosts).
- Verdict cache (host only, images without the flag started untrusted):
  `programs_registry.spawn` remembers accepted flash allocations
  (`FlashRegistry::is_verified`, 32 entries); every
  `write_chunk`/`erase_chunk` overlapping an entry clears it. Devices
  verify such starts every time.
- `toit.run --verify` uses the same verifier for format 2;
  `--emit-canonical=FILE` writes the canonical form.
- The shipped certificate: `snapshot.launch` gets the bundle's
  `certificate` member (system/extensions/host/toit.run.toit); `toit.run
  --verify` uses it (`--no-certificate`, `--require-certificate`).
  `programs_registry.spawn` (flash) passes none: hosts infer; on devices
  the installer verifies with the trailing block of the image (format
  note 18, "What the installer does").

Trusted format-2 programs are verified only with `-Xverify`/`TOIT_VERIFY`
(trusted rules).

## What is trusted

| File | Role |
|---|---|
| `src/from_vm.rs` | Views VM memory as the abstract program: the tables are borrowed as slices (`Converted::program()`/`split()` give a `VProgram`; the `V2Method` array is viewed as `VMethod`, whose layout is asserted equal at compile time); the 23 builtin class ids are decoded; roots, globals, literals are converted to values and followed breadth first through the program image (work list, no recursion), one object at a time (`Objects`, a `heap_check::ObjStream`). An object's kind is its header's class tag, which must equal its class's tag; an instance has its class's field count (`class_bits`), as the core's `instance_fields` reads it; strings and byte arrays (internal or external) must lie in the image. Every read is bounds-checked against `[program_heap_start, +program_heap_size)`. |
| `src/verify.rs` | The verdict, the duties of spec/SOUNDNESS.md "What the VM checks outside the verifier": `x_wf_program2` (the inference and the heap check require it); the proven `heap_check::x_loaded_ok_stream` over the converted objects (accepts only if their heap satisfies `loaded_ok`), and the conversion must complete without error; the untrusted `infer::infer_global`, whose trusted fields (`global_count` = the globals' count, `prim_arity` = the VM's table) are set here; and the proven `check::verify` with the inference's oracle (= `g_ok && split_ok`, which implies `accepts` of the assembled certificate, untrusted rules), or with a shipped certificate the proven `cert::verify_shipped` (true only if a certificate with these trusted fields is accepted). The rest is diagnostics. |
| `src/ffi.rs` | C ABI; panics reject (hosts). |
| `src/counting.rs`, `src/clock.rs` | Counting allocator and phase times (measurement; hosts). |

Not trusted: `canonical.rs`, `tables.rs`, the `toit_vmverify_canonical`,
`toit_vmverify_mem` and `toit_vmverify_fuzz` tools (tests).
`v2/infer.rs` stays untrusted (it only produces the certificate).
The heap check is verified (`x_loaded_ok_stream`; `x_loaded_ok` for a heap
in memory is proven equal to `loaded_ok`, including the bound of 2^29
objects).

Correspondence with the dump path:
`verified/tools/vmverify_differential.toit` compiles every suite program
in format 2 and compares the canonical form of the program built from VM
memory (`toit.run --verify --emit-canonical`, which
converts every object with `collect_heap`) with the one the reference
loader builds from `tools/spec_dump.toit`'s dump
(`toit_vmverify_canonical`). Objects are renumbered breadth first from the
roots, globals and literals; large integers compare by value. Result
(2026-11-10, borrowed tables and object stream): **439 of 439** compilable programs identical (the 4 others are negative compile tests).
`verified/check.sh --tests` runs the unit tests, a sample of the
differential test and the fuzz reproducers (`tests/findings.sh`).

## What the C++ format-2 loader still checks

`V2MethodTable::compute` only decodes: the tag, bytecodes below 2^28,
1..2^24 methods, header flags, LEB128 numbers in shortest form, selector
below 0xffff, non-empty receiver ranges and lambda/accessor operands
inside 16 bits, and that every body lies inside the bytecodes. That is
what it takes to build the table at all, and `entry <= end <= len` is what
the core's views rely on (core/TRUSTED.md V3). Everything it used to check
besides (dispatch entries, receiver ranges, opcodes, this-field accesses,
branch targets, terminators, instructions crossing the end, HALT 2/3,
failure literals) is the verifier's, which checks it on reachable code
only; the loader no longer looks at instructions, so the two cannot
disagree on unreachable code. The snapshot reader keeps its own
format-independent checks (object tags against classes, instance sizes,
table sizes): it needs them to allocate objects, and format 1 relies on
them. The core keeps its entry checks (table sizes, literals) and every
run-time check of a stuck state.

## Memory

The verifier keeps no data proportional to the program except small
per-method tables (about 36 bytes per method):

- **Program**: borrowed in place (`VProgram` over the VM's tables and its
  `V2Method` array); only the 23 builtin ids, the roots, literals and
  globals are converted (16 bytes per value).
- **Heap**: checked one object at a time as it is converted
  (`x_loaded_ok_stream`); the conversion keeps a work list and an
  address-to-id map (about 40 bytes per object), freed before the
  inference.
- **Certificate, global part** (`XGlobal`): block-parameter bits with a
  4-byte offset per method, a 4-byte context index per method plus the
  contexts of block methods (their kinds, 12 bytes per slot: about half
  of the global part), selector representatives (4 bytes per selector),
  and the pins (one map per non-local-branch target).
- **Certificate, maps**: one method at a time. The inference keeps, for
  the method it analyzes, a node index per bytecode byte (4 bytes), a
  work-list flag, the nodes (16 bytes per new slot; maps share their
  bottoms) and, in the global phase, sparse origin lists; the checker
  gets the same maps (`XMaps`) and drops them after the method. Budgets
  (`infer.rs`: 16 nodes and 64 origin words per byte) bound what a
  malformed method can make it allocate; compiled code needs at most 3
  and 22.

So the peak is roughly `36 B x methods + 16 B x values + 40 B x objects +
largest method's maps`, about 40 to 80 KB for programs of tens of KB of
bytecode, against a few hundred KB of free heap on the Phase 5 device.
Further reductions if needed: the contexts' kinds could share nodes like
the maps (half of the global part), and the heap's id map could be a
bitmap over the image.

## Fuzzing the entry point in-process

`src/bin/toit_vmverify_fuzz.rs` calls `toit_vmverify_verify` (the C entry
point the VM calls) on mutated copies of the exact input the VM hands it:
`toit.run --verify --emit-canonical=X.tables X.snapshot` saves the
`toit_v2_program` tables, the program image, the globals and the
primitive table (`tables.rs`; references are relocated to the copy).
Mutations: method table fields (bounds, selector, arity, kind, receiver
range), bytecodes (half of them near a method entry), dispatch entries,
class tables, invoke offsets and entry points, builtin ids, roots,
literals and globals, image words, truncated tables, the max height and
primitive arities; one to four per mutant. A verifier panic (result
`INTERNAL`) or a call over 2 s is a finding. `tests/fuzz_tables.sh` runs
it on hello world, lambda-test, exception-test, class-id-test and
task-test.

Runs (2026-11-10, 8 processes x 15 minutes each, `--seed 101` and, on
the final code, `--seed 301`): 428,561 and 445,655 mutants; on the final
code 101,454 accepted, 86,197 malformed memory, 242 heap contract,
147,283 tables, 110,479 methods rejected; **0 verifier panics, 0 calls
over 2 s** (slowest 261 ms; largest peak 485 KB). The inference of the
previous branch panicked on such inputs (PHASE4-REQUESTS.md R6; 208
caught panics in one launch-mode run).

With shipped certificates (`tests/fuzz_tables.sh --certificates`: each
program's certificate from `toit_vmverify_certify`; a third of the mutants
mutate the tables and keep the certificate, a third mutate the certificate
(header words, table words, records copied over others, bytes of the maps
stream, truncation, growth), a third both), 2026-11-11, 8 processes x 15
minutes, `--seed 501`: 402,987 mutants; 39,475 accepted, 52,160 malformed
memory, 155 heap contract, 72,617 tables, 54,968 methods, 183,610
certificate rejected; **0 verifier panics, 0 calls over 2 s** (slowest
540 ms, under load; largest peak 281 KB).

## no_std (Phase 5)

Without the `std` feature this crate and verified/spec are `no_std` +
`alloc` (verified/core always is): no panic catching (a panic aborts; the
inference is total), no phase times, no counting allocator, no test
support, `BTreeMap` instead of `HashMap`. With `device-runtime` (devices)
the crate supplies the global allocator (the VM's malloc/free/realloc)
and the panic handler (`toit_vmverify_panic`, FATAL): src/device.rs. The
device library is built with the Cargo profile `device` (panic = abort,
LTO). `tests/nostd_check.sh` builds spec, core and the device library for
`riscv32imac-unknown-none-elf` and `riscv64imac-unknown-none-elf`;
`tests/device_size.sh` measures the linked size by component
(verified/core/PROGRESS.md, "Phase 5"). ESP32-C6/H2 firmware links it
with the menuconfig option `TOIT_VERIFIED_CORE`
(toolchains/idf/components/toit).
