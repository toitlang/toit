# RP2040

The port supports the 2 MiB Raspberry Pi Pico (`pico`), official Pico W
(`pico_w`), and Pico W-2023 clone (`pico_w_2023`). It provides the VM,
peripherals, persistent containers and storage, and USB firmware updates.
Wi-Fi is not supported in this port. The W-2023 has an ESP8285 on GP0/GP1;
the official Pico W uses a CYW43439. Board reservations keep radio and supply
pins separate from ordinary peripherals.

## Building

Install the host Toit build dependencies, CMake, Ninja, pkg-config, libusb
development files, Python 3 with pyserial, and an Arm GNU
`arm-none-eabi` toolchain with newlib and C++ libraries. From the repository root:

```sh
make rp2040-setup
make rp2040-recovery RP2040_BOARD=pico_w_2023
make rp2040 RP2040_BOARD=pico_w_2023
make rp2040-test
```

Setup uses the same pinned Pico SDK and workspace-local picotool as RP2350.
These commands do not flash hardware. `RP2040_BOARD` defaults to `pico`;
each board gets separate build directories. Use `RP2040_CMAKE_FLAGS` to pass
additional CMake options, such as a different `PICO_TOOLCHAIN_PATH`.

The default application is the VM smoke test. To select an application:

```sh
make rp2040 RP2040_BOARD=pico_w_2023 \
  RP2040_PROGRAM=/absolute/path/to/main.toit \
  RP2040_PROJECT_ROOT=/absolute/path/to/package
```

The project root defaults to the application's directory. The application is
compiled separately from the system container, using its own package root.
Snapshot dependency files track imported source changes.

The application binary is `build/rp2040-BOARD-vm/toit-rp2040.bin`. It is linked
for the persistent recovery loader and cannot be installed as standalone
firmware. Follow the [recovery and upload instructions](../tools/rp2040/README.md)
for initial loader installation and subsequent USB updates. Initial installation
requires BOOTSEL; ordinary application updates do not.

## Firmware envelopes

`make rp2040-envelope RP2040_BOARD=pico_w_2023` builds a native base and
`build/rp2040-pico_w_2023-envelope/firmware.envelope`. The envelope contains the
system snapshot and accepts ordinary container installation, assets and
configuration through the firmware tool:

```sh
toit compile -s -o app.snapshot app.toit
toit tool firmware -e firmware.envelope container install \
  --output application.envelope app app.snapshot
toit tool firmware -e application.envelope extract --format=binary \
  --config config.json --output application.bin
```

Use a matching SDK/compiler. From this checkout, `build/host/sdk/bin/toit run
--project-root tools tools/firmware.toit --` runs the current tool source.
Extraction also supports `--format=ubjson` with image/config part boundaries.
The extracted binary is an update for the existing persistent recovery loader;
use `toit tool firmware -e application.envelope flash --port PORT`, the bundled
`rp2040-ota-upload` executable, or `system.firmware.FirmwareWriter` to install it.
It is not a standalone ROM-bootable recovery image. `make rp2040-bundle RP2040_BOARD=pico_w_2023` produces a standalone archive
with a loader-only UF2, system firmware, envelope, native uploader and
[installation instructions](rp2040-envelope-bundle.md). The native uploader
requires no Python at runtime. Initial loader installation uses ROM BOOTSEL;
`firmware flash --bootloader` remains unsupported for RP2040.

Run `python3 tools/rp2040/tests/envelope-test.py BUILD_DIRECTORY` against an
envelope build for host integration tests. It retains an extracted hardware
fixture under `BUILD_DIRECTORY/envelope-tests/firmware.bin`.

## Runtime

The VM runs on core 0 under FreeRTOS. Core 1 is unused. GPIO, ADC, PWM, UART,
I2C, SPI and PIO share the RP2350 drivers, with RP2040 hardware capabilities
checked explicitly. GPIO numbers are chip GPIO numbers, not header positions.
Use `import rp2040.pio` for the PIO library.

The shared APIs have the following RP2040 restrictions. Passing deprecated
`gpio.Pin` objects to peripheral constructors is not supported; pass integer
GP numbers instead. Pin reservations prevent conflicting peripheral owners,
and board-reserved radio/supply pads are unavailable except through their
designated interfaces.

| API | RP2040 behavior and limits |
| --- | --- |
| ADC | GP26–29, 12-bit conversion, nominal 3.3 V scaling; board reservations still apply. `max-voltage` does not select attenuation. |
| PWM | Two channels sharing a hardware slice must belong to the same `Pwm`, since they share a frequency. Aliased slice channels cannot be allocated twice. |
| UART | UART0/1 pin mappings, 5–8 data bits, 1 or 2 stop bits, parity, CTS/RTS and half-duplex RS485. UART_AUX, IrDA, 1.5 stop bits, appended breaks and control-flag access are unavailable. |
| I2C | Controllers use 7-bit addresses. Targets and register targets support 7/10-bit addresses, general call and response-time stretching. Address-only `Bus.test`/`scan` probing is unavailable. |
| SPI | Controller modes 0–3; target modes 1/3 only. Command and address bits together must be byte-aligned. Nonzero CS setup/hold cycle requests are unavailable. |
| PIO | Two blocks, four state machines per block, PIO version 0. RP2350 extended FIFO modes and IRQ MOV-status selection are unavailable. |

These are API capabilities, not a claim that every configuration has been
validated on hardware. The readiness section records the tested scope.

`rp2040.unique-id` returns the external flash chip's eight-byte identifier,
matching the USB serial number. `device.hardware-id` derives a UUID from it.
`rp2040.reset` releases runtime resources and restarts the installed firmware.
An application watchdog owns the hardware timer while armed; the boot task
only feeds the runtime's eight-second health watchdog while the application
watchdog is stopped. See `system.watchdog` for the timeout limits.

A dedicated system container provides container management and RAM/flash
storage and firmware services. The bundled application runs in its own process.
USB standard input belongs to application readers. Selecting 1200 baud on the
USB serial interface requests recovery without consuming any input bytes;
the system process tears down the VM before rebooting into the loader. The
uploader does this automatically, including after the application exits.
Other baud rates do not request recovery. USB CDC data has no physical baud
rate, so ordinary terminals should use 115200 rather than the reserved 1200.

The flash layout reserves 56 KiB for the persistent registry and two 960 KiB
application areas. Updates preserve the registry and can resume interrupted
installation. The current loader provides recovery, but no automatic rollback
to the previous firmware. Images are CRC checked, not authenticated.

Dynamically installed containers, their assets, and storage share that 56 KiB
registry. Each installation needs a contiguous free area. Bucket replacement
also needs room for both old and new values until the write succeeds. Bundle
larger applications and assets into the firmware envelope instead. Exhaustion
raises an error; rejected bucket updates leave existing values unchanged.

Bucket replacements carry generation numbers, so recovery selects the newest
committed allocation and reclaims its predecessor. Headers are invalidated
before payload erasure. Existing buckets using the older metadata format remain
readable and migrate on their next write. If multiple legacy allocations for
one bucket survive an earlier interrupted write, their order cannot be recovered;
the service reports `Ambiguous bucket generations` and preserves them.

`system.firmware.map` exposes the running application image. `FirmwareWriter`
accepts a complete raw image linked for `0x10020000` (from 0 to its exact size),
checks an optional SHA-256, and publishes the pending descriptor only after
flash read-back and vector validation. Flash work uses a native worker with a
copied sector buffer; waits suspend Toit tasks. `firmware.upgrade` restarts into
the committed image. A reboot after commit also installs it. There is no trial
boot or rollback: the corresponding capability queries return false and
`rollback` throws `UNSUPPORTED`. Firmware regions are not exposed (`uri` is null).
The loader's numeric image version is incremented by service updates.

Cryptographic random output uses mbedTLS CTR-DRBG, seeded and reseeded through
the entropy collector. The RP2040 input mixes Pico SDK ROSC samples and system
state; this board has no dedicated hardware TRNG. The VM requests 32 fresh
oscillator samples per SDK output word. Conditioning and regression checks do
not establish a measured entropy bound or resistance to physical manipulation.
RSA key generation uses the asynchronous worker, allowing VM timers and GC to
continue. Hardware fixtures cover random buffers/reset, RSA cancellation, EC,
and mutual TLS with hostname/CA verification against OpenSSL.
The shared RP2040/RP2350 mbedTLS configuration enables its standard NIST-prime
optimization. The Pico regression covers P-256, P-384 and P-521 signatures,
invalid signatures and shared secrets.

TLS checks certificate validity dates against the software wall clock. Set it
with `rp2040.set-real-time-clock` from a trusted time source before connecting.
The clock starts at the Unix epoch after every reset; there is no battery-backed
clock or automatic time synchronization. An unset clock rejects certificates
whose validity period has not begun. Changing the wall clock leaves monotonic
timers unaffected.

## Native memory

The VM, FreeRTOS and libc share a page-aware allocator over the linker-defined
SRAM heap. It allocates VM pages directly and uses reclaimable arenas for small
native allocations. This avoids requiring alignment slack when reusing a freed
4 KiB VM page. `system.process-stats` reports the real system free memory and
largest free block. Total free memory does not guarantee that a particular
contiguous or aligned request can succeed.

`system.serial-print-heap-report` prints native heap and calling-process
accounting. The hardware memory-pressure fixture checks rejected allocations,
retained data, subsequent PIO DMA/storage RPC and balanced external-buffer
accounting. Privileged OOM recovery is tested separately from application OOM.

## Validation scope

Earlier local hardware validation used the Pico W-2023. The plain Pico and
official Pico W variants were checked by building and packaging their firmware.
The hardware fixtures cover VM/GC and native memory pressure, watchdog and
native-failure recovery, GPIO/ADC/PWM/UART/I2C/SPI/PIO, asynchronous cleanup,
persistent containers/assets/configuration, storage exhaustion and interrupted
writes, USB input/output and recovery, and cryptography/TLS over USB.
See [the manual fixtures](../tests/hw/rp2040/README.md) for wiring and execution.

Storage interruption tests model partial NOR operations and resets; they do not
establish behavior during electrical brownouts. ADC checks cover the combined
DAC/ADC path on the rig, not calibrated absolute accuracy. I2C fixtures use
internal pulls and do not establish electrical timing margins for other wiring.
Random-output checks verify functional behavior without measuring an entropy
bound. Each peripheral's documented restrictions still apply.

The last pre-rebase loader validation, on October 6, 2026, installed and read
back the exact distribution loader, tested reply backpressure and abandoned
uploads, and recovered after normal and exceptional application exit. All three
board bundles passed envelope and standalone-uploader checks. These are
historical local results; rebased builds and CI are separate validation, and
hardware behavior must be checked again before a release.
