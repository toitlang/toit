# nRF5340 / Zephyr port

Experimental Toit port for the Ebyte E83-2G4M03S-TB (nRF5340 application core).
The port now targets Zephyr through a reusable `TOIT_ZEPHYR` backend. Zephyr
owns startup, threads, timers, memory protection, and peripheral drivers;
Toit retains its VM, scheduler, garbage collector, and language APIs.
The initial nRF-specific FreeRTOS prototype has been superseded.

The firmware runs in Secure state with 1 MiB application flash and 512 KiB
RAM. The network core now runs Zephyr's BLE HCI IPC controller. The console is UARTE0 on P0.20 TX / P0.22 RX
at 115200 baud through the board's USB-TTL connector. Native USB is unused.
The pending Pico worktree remains independent and has not been edited.

## Build and run

Prerequisites: CMake, Ninja, a host C/C++ toolchain, Arm GNU embedded GCC with
newlib and libstdc++, Python with venv and pyserial, Git, and the repository's
existing mbedTLS dependency. Building OpenOCD additionally requires autotools,
libtool, make, pkg-config, and libusb and JimTcl development files. Zephyr
requires Python 3.12 or newer. On Ubuntu 24.04 the additional embedded/debugger
packages include `gcc-arm-none-eabi`, `libnewlib-arm-none-eabi`,
`libstdc++-arm-none-eabi-newlib`, `device-tree-compiler`, `gperf`,
`python3-venv`, `python3-dev`, `python3-serial`, `libusb-1.0-0-dev` and
`libjim-dev`; the host compiler, CMake, Ninja and autotools are also required.

```sh
bash tools/zephyr/setup.sh
bash tools/nrf5340/setup.sh --openocd
cmake -S . -B build/host -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_TOOLCHAIN_FILE=toolchains/host.cmake
cmake --build build/host --target build_tools -j4
(cd tools && ../build/host/sdk/bin/toit pkg install)

export ZEPHYR_BASE="$PWD/.cache/zephyr-workspace/zephyr"
export ZEPHYR_TOOLCHAIN_VARIANT=gnuarmemb
export GNUARMEMB_TOOLCHAIN_PATH=/usr
export CCACHE_DIR="$PWD/.cache/ccache"
cmake -S toolchains/zephyr -B build/zephyr-nrf5340 -G Ninja \
  -DBOARD=e83_2g4m03s_tb/nrf5340/cpuapp \
  -DPython3_EXECUTABLE="$PWD/.cache/zephyr-venv/bin/python"
cmake --build build/zephyr-nrf5340 -j4
```

The setup script pins Zephyr v4.4.1 at
`1f6485eca25431b5ff27ce9a754218c9e559bbbb` and fetches CMSIS, Nordic HAL,
OpenAMP, libmetal and Mbed TLS modules at the revisions in its manifest. It
uses an isolated Python venv. The Mbed TLS module provides Zephyr's custom PSA
provider Kconfig definitions; the VM links Toit's existing Mbed TLS library.
It also applies `tools/zephyr/patches/spi-dynamic-cs.patch`, which retains GPIO
chip-select support for runtime SPI configurations when devicetree declares no
static chip selects. `smp-h8-selftest-endian.patch` corrects the byte order of
the SMP h8 self-test vectors to match Zephyr's separate crypto unit test and
the Bluetooth specification. It does not change the cryptographic algorithm.
The script accepts either a clean checkout, the previous SPI-only setup, or
both exact patches, and rejects unrelated tracked Zephyr modifications.
Override `GNUARMEMB_TOOLCHAIN_PATH` if the compiler is installed elsewhere.

## Implementation and next work

`TOIT_EMBEDDED` separates shared embedded behavior from FreeRTOS-specific
APIs. Existing FreeRTOS targets still select that shared behavior. The Zephyr
backend uses kernel threads, mutexes, condition variables, monotonic ticks,
and newlib allocation. The current 64-bit atomic helpers require a single
core; they do not synchronize with the nRF5340 network processor.

GPIO numbers use `32 * port + pin`: P0.08 is 8 and P1.04 is 36. The
`toit,platform` devicetree node lists GPIO controllers and restricted pins.
Pin reservations are shared by GPIO and the peripheral drivers.
The Zephyr event worker coalesces interrupt flags per resource and
holds the event-source lock during dispatch, so queued events cannot retain
pointers to closed resources. Nordic edge interrupts currently consume GPIOTE
channels; exhaustion is reported by the driver rather than silently polling.

The [wired peripheral qualification runner](../tests/hw/nrf5340/README.md#paired-toit-gpio-test)
packages all eight GPIO/UART/I2C/SPI/ADC/PWM suites against one default envelope,
runs them on the documented ESP32 rig, restores the supplied normal firmware,
and compares both persistent partitions. This is the repeatable hardware check
for changes to the common runtime or peripheral backends; the build-only check
above does not establish electrical behavior.

Toit obtains entropy through Zephyr's entropy API. A local nRF5340 driver
reads CryptoCell's RNG using the factory oscillator calibration and hardware
health tests described in the [Nordic product specification](https://docs.nordicsemi.com/r/bundle/ps_nrf5340/page/cryptocell.html).
mbedTLS conditions the entropy before use by Toit's entropy mixer. Failures
are reported rather than replaced with deterministic random data. This is
bring-up validation, not statistical qualification or security certification.

The native UART lifecycle probe established a usable dynamic-pin sequence:
suspend the device, update its default/sleep pinctrl states, then resume it.
It passed 64 remaps between P1.04/P1.05 and P0.08/P0.09. The ESP32 checked
both TX lines after every open and close (258 fixture requests), including
release of the old pin. This verifies routing and release, not UART payloads.

Repeated suspend/deinit/init is unsuitable with the pinned Nordic UART driver:
it failed with `-ENOMEM` on zero-based cycle 29. Its initialization allocates
an ENDTX-to-STOPTX DPPI connection, while deinitialization only checks the power
state. The suspend/resume path preserves that allocation. Toit's UART backend
initializes UART1 once, then uses suspend/resume for reopen. Initialization
is deferred at boot so it does not drive unclaimed pins. The port holds an
HFXO clock request while open and releases it after stopping DMA and suspending
the peripheral. RX uses two 256-byte DMA buffers feeding a 4 KiB software ring
(16 KiB with `--large-buffers`); TX uses a stable 1024-byte staging buffer.

Baud changes stop RX before reconfiguration and restart it while holding the
event-source lock. The buffer callback must accept requests before
`uart_rx_enable` returns: delaying this until after the call caused the first
second-buffer request to be dropped and overflowed reception at high rates.
The paired test exercises this ordering at each baud change.

The current board exposes one application UART in addition to its console.
RTS/CTS are routed when both pins are supplied. Flow-controlled RX reserves
space for both 256-byte DMA buffers before accepting another buffer. When
the native ring fills, the receiver stops and deasserts RTS; draining the ring
explicitly wakes the event worker to restart reception. This also applies
when baud configuration is changed while RX is paused. Without flow control,
the existing receive-overflow accounting remains in use.

The paired flow-control test reproduced 16896 dropped bytes with the previous
driver. After the fix it passed 32768-byte streams at 115200 and 1000000 baud
with both 4 KiB and 16 KiB receive rings, despite delaying the Toit reader for
two seconds. It also passed CTS blocking/release, reconfiguration while paused,
subsequent transfers, close while RX is paused, close with CTS blocking TX,
and process teardown with blocked TX. The host verified RTS pin release.
All 35 fixture requests passed; no rewiring was needed because RTS/CTS used
the existing SPI signal wires. The full existing UART regression then passed
all 316 requests, including deliberate overflow without flow control and
64 close/remap cycles.

Inversion, RS485/IRDA, break transmission and modem control flags
are not implemented. Priority hints do not change the
Zephyr IRQ priority. The driver validates supported baud rates and framing.

### Console input

`io.stdin` now reads raw bytes from the board's USB-TTL console at 115200 baud.
It uses UARTE0 with two 256-byte DMA buffers, TIMER1 for receive byte counting,
and a shared 4 KiB native ring allocated while readers exist. The application
UART remains UARTE1 with TIMER0. Continuous input is delivered in DMA blocks;
idle input is delivered after a 1 ms receive timeout. Output remains owned by
Zephyr's polling console. Native USB and `uart.Port.console` are not implemented.

The stdin stream is shared across containers; the first reader consumes the
available bytes. It has no serial EOF indication. Cancellation stops the Toit
wait without stopping other readers. The last container releases the callback
and ring only after DMA reports RX_DISABLED. Buffer overflow raises EOVERFLOW
(newlib's "Value too large for defined data type") and discards the incomplete
native buffer. Applications that buffered part of a message in the Toit reader
can call `io.stdin.clear` before resynchronizing their protocol. This console
has no RTS/CTS flow control; a sender must avoid overrunning a stalled reader.

The paired stdin suite passes 29 binary transfers, including all byte values,
16385-byte continuous input, sixteen sole-owner container lifetimes, competing
readers, task/deadline cancellation, overflow/recovery and final teardown with
a blocked reader. It also checks 8192 bytes echoed on the application UART
while another 16385 bytes arrive on stdin. The existing UART regression passes
all 316 fixture requests with the new console configuration. Evidence is in
`build/nrf5340-stdio/final-hardware.log` and `uart.log`.
The power suite also passes all four boots and 40 fixture requests with a
blocked stdin reader before each shutdown (`power.log`): both GPIO wake levels,
timed restart, final teardown and peripheral recovery remain functional.
The same 29-transfer suite passes in the optional BLE build with an advertiser
active (`ble-hardware.log`), including concurrent application UART traffic and
joint VM teardown. This checks local coexistence, not peer reception or GATT
traffic. Physical UART line-error injection and current draw are unqualified.

The initial one-byte IRQ implementation overflowed its software ring on the
long transfer; diagnostics reported no UART hardware overrun. DMA batching
fixed that case without increasing the ring capacity. The qualification images
contain no temporary diagnostic prints. See the fixture README for commands.

I2C uses a dedicated worker because the pinned Zephyr Nordic driver exposes a
blocking transfer API. Each job owns native TX/RX buffers until completion;
the event source only dispatches a completion for a live, finished job. Closing
or cancelling retires the job before releasing those buffers. Worker stacks
are allocated on bus open and joined/freed on close. TWIM2 itself initializes
once and uses suspend/remap/resume between owners, independently of UART1.

The driver has a 500 ms timeout per message, so very long transfers may time out
even on a healthy bus. Cancellation waits for driver retirement and can exceed
the caller's deadline by the remaining transfer time (potentially both legs of
a combined operation). This wait does not hold the shared event-source lock.
Custom clock-stretching timeouts, disabled ACK checks, 10-bit addresses, and
I2C target mode are not implemented. Accepted device frequencies are 100 and
400 kHz; only 100 kHz has been tested on this rig. Requests below 100 kHz are
rejected rather than silently clocked faster. Higher-speed qualification remains
deferred until external pull-ups are available.

SPI owns stable native DMA buffers until the asynchronous transfer finishes.
Bus reservation supports held CS across transfers; releasing the reservation
also releases CS on exceptions. Closing the last-used device invalidates the
Nordic driver's cached configuration through suspend/resume, preventing reuse
of a freed configuration address from preserving another device's settings.
The controller initializes only when claimed, and pin ownership covers CS/DC
as well as clock and data pins.

SPI cancellation currently drains the accepted transfer before releasing DMA
buffers, so it can exceed the caller's deadline. Transfers are limited to
65,536 bytes including prefixes, with frequencies starting at 125 kHz. The
driver may round frequencies down to supported rates; rates above 4 MHz have
not been tested. Command/address prefixes must have a byte-aligned combined
length. Custom CS setup/hold cycle counts and SPI target mode are not
implemented. The original ESP32 fixture limits full-duplex tests to 64 bytes;
4096-byte transfers were tested separately in each direction.

ADC uses the Nordic SAADC through Zephyr with 12-bit single-ended conversions,
the internal 600 mV reference, and 40 microsecond acquisition time. The board
maps GPIO pins 4–7 and 25–28 to AIN0–AIN7, following the
[Nordic pin assignments](https://docs.nordicsemi.com/r/bundle/ps_nrf5340/page/chapters/pin.html).
`max-voltage` selects the smallest covering range from 0.15, 0.3, 0.6, 1.2,
1.8, 2.4, 3.0, and 3.6 V; the default is 3.6 V. This converter range does not
change the pin's permitted supply-relative input voltage. Differential inputs,
internal supply measurements and continuous/timed capture are not exposed.

ADC channel setup and sampling are serialized together. Each resource reserves
its GPIO, disables the digital input/pulls, and runs offset calibration on its
first read. A single hardware slot is reconfigured for each call, avoiding
stale channels in later scans. Synchronous requests take at most 64 samples;
larger Toit averages yield between chunks so timers and cancellation can run.
The native probe measured at most 3875 microseconds for a 64-sample read.
Cancellation takes effect between chunks, with no pending DMA to retire.

The backend deliberately uses zero-interval simple-mode sequences. In the
pinned Zephyr v4.4.1 driver, the internal-timer path bypasses requested offset
calibration and reports completion both at DONE and FINISHED for a one-sample
sequence. That leaves a semaphore token which can let the next read return
before DMA finishes. The initial Toit test caught a raw reading of 0.896 V
immediately after a correct 2.854 V average on the same input. Simple mode
avoids both issues without another Zephyr patch. Calibration is a separate
single-sample operation so subsequent samples do not repeat it unnecessarily.

PWM now has a Toit backend with passing board and ESP32 fixture tests.
The four Nordic PWM controllers are exposed through `gpio.pwm.Pwm`, with four
independently adjustable channels per generator. Pins come from the shared
ownership pool; the legacy borrowed-`Pin` form is also supported. Controllers
initialize only when the first channel is opened. Channel/process cleanup stops
DMA before releasing pins, and closing the last channel disconnects all PSEL
outputs. Changing frequency or pin routing suspends and resumes the controller,
so it can interrupt one period on its other channels; at the lowest frequency
the synchronous driver stop can delay the calling VM thread by about 250 ms.

Accepted integer frequencies are 4 through 5,333,333 Hz, subject to the
constructor's `max-frequency` bound. The backend chooses the finest prescaler
and rounds to a representable period; `frequency` reports the resulting integer
frequency. Duty factors are rounded to the same counter resolution, clamped to
0..1, and queried as the resulting fraction. NaN is rejected. These limits
follow the 16 MHz clock, dividers 1..128, and counter range 3..32767 in the
[Nordic PWM specification](https://docs.nordicsemi.com/r/bundle/ps_nrf5340/page/pwm.html).
`max-frequency` bounds requests; unlike ESP32 LEDC, it does not fix the duty
resolution for lower frequencies.

The normal and BLE firmware builds include the backend. The host arithmetic
suite passes under ASan/UBSan across every accepted integer frequency, with
additional duty sweeps, endpoints and invalid-input checks. The prepared
`pwm-nrf5340.toit` suite covers controller/channel exhaustion, remapping, pin
conflicts, borrowed pins, process cleanup, and pad read-back of slow waveforms.
That suite passes on the board: sixteen remap cycles, invalid arguments and
NaN handling, clamping, controller/channel exhaustion, borrowed-pin ownership,
pad read-back at 50/100 Hz, and child-process cleanup. The paired external suite
also passes all 69 requests: four independent controllers at 1/2/5/10 kHz,
25/50/75-percent duty measurements, shared frequency changes, duty at 4 Hz,
channel removal/reuse, and four 10 kHz endpoint/recovery cycles. Each endpoint
cycle includes a PWM-train RMT positive control and completed idle captures for
both 0% and 100%, followed by opposite-pull GPIO checks. Both suites complete
VM teardown; the ESP32 verifies all four pins with both pull-up and pull-down.
Evidence is in `build/nrf5340-pwm/paired-final.log` and `lifecycle.log`.
External frequency qualification above 10 kHz, precise clock accuracy and
scheduling latency during lowest-frequency stops remain untested. Hardware
access was restored when the user restarted the failed PC USB controller.

`import zephyr` exposes `reset`, `reset-reason`, and `supported-reset-reasons`.
Reset uses Toit's existing VM shutdown path, then Zephyr's `sys_reboot` after
native resources have been released. Reset reasons are Zephyr HWINFO bit masks,
not the ESP32's enum values. The current driver reports a supported mask of
`0x1bb`; a zero cause means no reported bits, not confirmed power-on. Each boot
captures and clears the hardware flags once, and all processes see that cached
value. The new primitive module is appended so existing module indices remain
unchanged.

`import zephyr.watchdog` exposes `watchdog-start --timeout=Duration`,
`watchdog-feed`, and `watchdog-stop`. It uses WDT0 with whole-millisecond
timeouts from 1 to 131071999 ms. The timer continues in ordinary CPU sleep and
pauses under a debugger. Starting again stops/reconfigures it; stopping frees
the reload channel. The watchdog is global, is not automatically fed by the
VM, and stays armed across process exit and VM teardown. Applications must
explicitly stop it when that is desired. The nRF5340's stop capability is
described in the [Nordic watchdog specification](https://docs.nordicsemi.com/r/bundle/ps_nrf5340/page/wdt.html).

### Power-off and timed restart

`zephyr.power-off --wake-pin=32 --wake-high=true --pull-down` stops the entire
VM, closes its resources, suspends the console, and enters System OFF. The wake
pin is configured only after teardown, so it may previously belong to a GPIO
or peripheral resource. High and low active levels and optional internal pulls
are supported; reserved pins and conflicting pulls are rejected. An already
active pin can wake immediately. Omitting the pin leaves wake to other hardware
sources, such as reset or a debugger. GPIO wake boots the system from scratch
and reports `RESET-LOW-POWER-WAKE`; Toit RAM state is not preserved.

The nRF5340's RTC cannot wake System OFF. The separate
`zephyr.sleep-and-restart (Duration --ms=750)` API instead tears down the VM,
suspends the console, waits in System ON with the Zephyr timebase running, and
requests a software reset. It accepts 1 ms through 24 hours; the duration starts
after resource cleanup. An armed watchdog is neither stopped nor fed and can
reset earlier. Ordinary Toit `sleep` continues to keep the VM and its resources
alive. See the [Nordic power-mode specification](https://docs.nordicsemi.com/r/bundle/ps_nrf5340/page/chapters/pmu/doc/pmu.html).

The paired hardware test passed GPIO wake in both directions, a 750 ms timed
restart (759 ms observed at the host), and subsequent UART, I2C, SPI, and ADC
operations. Each shutdown included an I2C transfer held pending by the ESP32,
a child blocked on UART RX, and an open ADC. The fixture verified released UART
and GPIO outputs before wake. A native probe independently passed both GPIO
wake directions. A second four-boot test passed already-active high and low
wake levels and watchdog expiry during a requested five-second System ON
sleep. The watchdog reset occurred after 1.513 seconds of that sleep (its
two-second timeout started before VM teardown), reporting `RESET-WATCHDOG`.

These are functional tests, not current measurements. The attached debugger
can cause System OFF emulation; normal-mode low-current qualification needs
debug release and pin reset plus a current measurement setup. See the
[Nordic debug-mode description](https://docs.nordicsemi.com/r/bundle/ps_nrf5340/page/debugandtrace.html).
The network core remains unused, so coordination with radio activity is not
covered. Reset-only power-off and the full 24-hour wait have argument-validation
coverage but have not been exercised end to end.

### VM error recovery

An uncaught exception or nonzero exit in a critical container causes the shared
container manager to terminate the system process. Zephyr now releases all VM
resources, prints the exit code, waits one second, and requests a cold software
reset. The delay limits repeated failing boots. A watchdog already armed by
the application remains active and may reset the device before that delay
expires. This policy handles `Scheduler::EXIT_ERROR`; native assertions and
kernel faults use the separate policy below.

Successful critical containers, explicitly stopped containers, and noncritical
container failures do not request this restart. Normal VM completion still
leaves the board idle; it does not enter system-off. An explicit `zephyr.reset`
continues to reset immediately after teardown.

The paired lifecycle test reproduced the former idle-after-error behavior and
verified the fix with both exit code 23 and an uncaught exception (code 1).
Each case kept an I2C transfer pending with SCL held low, a child process waiting
on UART RX, and SPI/ADC resources open. The ESP32 checked released output pins
during the error backoff. After the software reset, the test performed UART
loopback, I2C reads, SPI full-duplex transfers, and an ADC reading from the ESP32
DAC. The same test checks ordinary error codes, critical success/stop, and
resource reacquisition without restarting. See `tests/hw/nrf5340/README.md` for
the commands and before/after evidence.

### Native fault recovery

`CONFIG_TOIT_REBOOT_ON_FATAL_ERROR=y` is the default. The port's Zephyr fatal
handler prints the numeric fault reason and requests an immediate cold reset.
Zephyr's C library already routes `abort()` to `k_panic()`, so Toit's native
`FATAL`/`ASSERT` path also reaches this policy. Zephyr supplies its architecture
fault diagnostics before calling the handler.

Unlike a controlled VM error, a native fault may arrive in an interrupt or with
damaged kernel state. The handler does not unwind VM resources, allocate memory,
flush libc streams, or sleep. Peripheral outputs are released by the hardware
reset. Reset-cause reporting shows a software reset; the preceding console
message identifies the native fault. There is no persistent crash record yet.
This cannot guarantee recovery from corruption that prevents the fatal handler
from running; an independently armed watchdog remains useful for CPU lockup.

Set `CONFIG_TOIT_REBOOT_ON_FATAL_ERROR=n` in a configuration overlay to retain
Zephyr's default halt-on-fault policy for debugging. The native test covers both
policies, including an SWD check of the halted program counter. See the hardware
test README for reproduction.

## Persistent storage

The current bring-up layout reserves 16 KiB for Zephyr settings followed by
the existing final 128 KiB for Toit storage.
This is not an OTA layout; MCUboot, image slots and update transport remain
undecided.

| Application flash range | Size | Use |
| --- | ---: | --- |
| `0x00000`–`0xdbfff` | 880 KiB | Linked Zephyr/Toit firmware and embedded program |
| `0xdc000`–`0xdffff` | 16 KiB | Zephyr settings, including future Bluetooth bonds |
| `0xe0000`–`0xfdfff` | 120 KiB | Toit allocation registry: buckets, regions and allocation headers |
| `0xfe000`–`0xfffff` | 8 KiB | Private recovery descriptor and page image |

The devicetree code partition bounds the linker, and `tools/nrf5340/flash.py`
rejects an oversized binary before opening serial or invoking OpenOCD.
Ordinary firmware flashing preserves storage. Allocation headers consume
space, and bucket replacement needs room for both old and new allocations;
120 KiB is the registry capacity, not guaranteed application payload capacity.
Raw `--partition` access is unsupported.

The optional `settings.conf` enables Zephyr's NVS settings backend with four
4 KiB sectors and data CRCs. Its hardware qualification passed 256 verified
512-byte updates, repeated garbage collection, value and deletion persistence
across resets, and preservation through firmware replacement. The entire
Toit storage partition matched the original backup after the test, and the
qualification removed its own settings keys. Evidence is in
`build/nrf5340-settings/hardware-slow/summary.json`. Physical power loss and
Bluetooth pairing are not covered by that test.

The original 1 MHz FTDI attempts stalled during flashing and sustained reads.
Resetting the adapter did not resolve that. A 250 kHz SWD clock with 64-byte,
paced backup reads completed the qualification. `flash.py --adapter-speed 250`
selects that clock; the default remains 1000 kHz. Failed attempts and the
original backups are retained in `build/nrf5340-settings`.

`system/extensions/zephyr/storage.toit` installs the existing storage service.
Flash buckets use the shared copy-on-write registry implementation, and RAM
buckets use volatile memory. The build enables Toit crypto because storage's
UUIDs require SHA-1. The Zephyr backend uses synchronous NVMC operations with
4 KiB erase pages and word-aligned programming. Nordic specifies at most two
programs of a word between erases in its
[NVMC specification](https://docs.nordicsemi.com/r/bundle/ps_nrf5340/page/nvmc.html).
The backend programs changed words only once, skipping erased/unchanged words.

To preserve Toit's arbitrary byte writes and repeated bit-clearing semantics,
changing an already programmed word stages the entire updated page in a
recovery journal. A CRC-checked descriptor is committed before erasing the
destination, and retired only after verifying the complete replacement. Boot
replays committed work before scanning the allocation registry. An update
still in staging leaves the old destination intact. Multi-page writes and
multiple bucket operations are not one atomic transaction.

A dense page rewrite measured 466–467 ms on this board; eight sparse byte updates
took about 2.9 seconds. Flash operations are synchronous and can delay Toit
tasks and interrupts; watchdog deadlines must allow for them. The two journal
pages are not wear-levelled, so repeated in-place byte updates are unsuitable
for high-rate logging. Reset injection is covered; brownout/power-cut testing
and endurance qualification remain outstanding. The original contents of the
reserved partition were backed up to `build/nrf5340-storage/before-storage.bin`
before the first storage test.

## Deploying applications from the PC

`tools/nrf5340/deploy.py` installs relocatable Toit images through the connected
FT2232H SWD adapter. This is a development transport for the fixed E83 bring-up
layout. It requires the exact running native firmware binary, which it copies
into the operation log directory and verifies against the target before and
after the operation. Container images must use the same SDK UUID. The native
firmware, data allocations and journal are preserved.

For a base firmware with no bundled application, configure and flash once:

```sh
cmake -S toolchains/zephyr -B build/zephyr-nrf5340 \
  -DTOIT_ZEPHYR_PROGRAM= -DTOIT_ZEPHYR_PROGRAM_ASSETS= \
  -DTOIT_ZEPHYR_BUNDLED_IMAGES=
cmake --build build/zephyr-nrf5340 -j4
mkdir -p build/nrf5340-deploy
cp build/zephyr-nrf5340/zephyr/zephyr.bin build/nrf5340-deploy/base.bin
python3 tools/nrf5340/flash.py build/nrf5340-deploy/base.bin \
  --serial /dev/serial/by-path/pci-0000:02:00.0-usb-0:2.3.3.3:1.0-port0 \
  --expect '[toit] reset cause=' --stop-after '[toit] reset cause='
```

The current system-only image measures 503,808 bytes of flash. Compile and deploy an
application using the matching host SDK:

```sh
build/host/sdk/bin/toit compile -s -o build/application.snapshot application.toit
build/host/sdk/bin/toit tool snapshot-to-image --format=binary -m32 \
  -o build/application.image build/application.snapshot
python3 tools/nrf5340/deploy.py --firmware build/nrf5340-deploy/base.bin \
  install build/application.image
python3 tools/nrf5340/deploy.py --firmware build/nrf5340-deploy/base.bin list
python3 tools/nrf5340/deploy.py --firmware build/nrf5340-deploy/base.bin \
  uninstall CONTAINER-UUID
```

Add `--assets PATH` to `snapshot-to-image` for an encoded assets file. Install
defaults to auto-start after reset; `--no-run-boot`, `--critical` and `--data`
control the container metadata. An identical installation is idempotent. The
tool rejects a matching ID with different contents or flags; explicitly
uninstall it first. To change versions, uninstall the previous UUID and install
the new image. This does not provide an atomic application-version swap.

`list` halts the core while reading and resumes it only if it was running.
`install` and `uninstall` reset the application core, including idempotent
operations. They preserve network-core flash and UICR. A committed storage
journal must first be recovered by booting the firmware. Data records and
checksum-valid programs from other SDKs remain reserved, even though those
programs will not run on the current firmware.

The installer writes into a free contiguous allocation, verifies the relocated
body and assets, then programs the allocation header last. An interrupted body
upload therefore remains unpublished. Uninstall erases only the program's
header page. Each operation checks the entire 128 KiB storage partition against
the planned change, leaving both before/after backups and `result.json` in a
unique subdirectory of `build/nrf5340-deploy`. Those snapshots describe the
state before the application runs again; application writes after reset are
separate. `--json` exposes the same result to scripts.

Optional `--serial PATH --expect TEXT --seconds N` arguments, placed before the
operation name, capture startup output. If the flash operation succeeds but
the marker is missing, `result.json` still records the verified operation.
Keep `base.bin` as the reference for the flashed firmware when building other
variants in the same CMake directory.

The adapter intermittently stalled during OpenOCD's 4 KiB `dump_image` reads.
The deployment tool instead reads 256-byte chunks; eight consecutive 128 KiB
reads passed at about two seconds each. A transport timeout invalidates the
connection, stops OpenOCD, and prevents further commands on that connection.
An incomplete programming/verification operation is not resumed automatically;
the log directory records this with `not-resumed.txt`. Reconnect and inspect
the backups before explicitly resetting or retrying. This path assumes the
current `0xe0000` storage base and 128 KiB reservation; changes to that layout
must update the deployment tool as well.

## Firmware envelopes

The Zephyr build now exports an envelope through the `toit_envelope` target:

```sh
cmake --build build/zephyr-nrf5340 --target toit_envelope -j4
build/host/sdk/bin/toit tool firmware \
  --envelope=build/zephyr-nrf5340/toit.envelope show
build/host/sdk/bin/toit tool firmware \
  --envelope=build/zephyr-nrf5340/toit.envelope extract \
  -o build/zephyr-nrf5340/envelope.bin
```

It includes the system snapshot and every application selected by
`TOIT_ZEPHYR_PROGRAM` and `TOIT_ZEPHYR_BUNDLED_IMAGES`, named `app0`, `app1`, etc.
Use `container install`, `container uninstall`, `--assets`, `--trigger`, and
`--critical` as with other envelopes. Both snapshots and relocatable 32-bit
images are supported, including images with inline assets. Separate assets
cannot also be attached to an image that already contains them. Container names
are exposed through `system.containers.images`.

To create an envelope manually from a system-only native build:

```sh
build/host/sdk/bin/toit tool firmware --envelope=build/nrf.envelope create zephyr \
  --firmware.bin=build/zephyr-nrf5340/zephyr/zephyr.bin \
  --system.snapshot=build/zephyr-nrf5340/boot.snapshot
build/host/sdk/bin/toit tool firmware --envelope=build/nrf.envelope \
  container install app build/application.snapshot
build/host/sdk/bin/toit tool firmware --envelope=build/nrf.envelope \
  extract -o build/nrf.bin
python3 tools/nrf5340/flash.py build/nrf.bin \
  --serial /dev/serial/by-path/pci-0000:02:00.0-usb-0:2.3.3.3:1.0-port0
```

Manual `create zephyr` includes only the supplied system snapshot; add other
containers explicitly. Extraction replaces the native binary's entire bundled
extension with the envelope's containers. The CMake target performs these adds
automatically. Keep the extracted binary as the exact reference for subsequent
SWD deployment operations.

The linker places the replaceable extension after all native flash content.
A `TOITZPH1` descriptor records its address, the firmware partition boundary,
and the native SDK UUID. The tool validates this descriptor, requires matching
SDKs, relocates each program at its final address, and preserves the native
prefix byte-for-byte. It rejects malformed images, duplicate IDs, conflicting
assets, a missing system snapshot, or anything exceeding the code partition.
The system snapshot must remain present. Older bring-up binaries without the
descriptor must be rebuilt before envelope creation.

This is experimental envelope kind `zephyr`. Application-only envelopes use
format 1003; nRF5340 envelopes containing a network controller use format 1004
(1001/1002 are used by the pending Pico ports). Older SDK tools reject format
1004 rather than silently dropping its controller image. The E83 application
is linked at address zero and remains limited to 880 KiB, preserving the
16 KiB settings and 128 KiB storage reservation.

With Bluetooth HCI IPC enabled, `toit_envelope` also builds Zephyr's `hci_ipc`
controller for the board's `cpunet` target and includes it in the envelope.
`TOIT_ZEPHYR_NETWORK_IMAGE` can select an existing matching controller binary;
`TOIT_ZEPHYR_NETWORK_BOARD` overrides the automatically selected network board.
For manual envelope creation, add `--network.bin=path/to/controller.bin` to
`create zephyr`. Container installation and removal retain the controller.
Extract and flash both cores together:

```sh
build/host/sdk/bin/toit tool firmware \
  --envelope=build/zephyr-nrf5340-ble/toit.envelope extract \
  --format=tar -o build/nrf5340-ble/firmware.tar
python3 tools/nrf5340/flash.py build/nrf5340-ble/firmware.tar \
  --serial /dev/serial/by-path/pci-0000:02:00.0-usb-0:2.3.3.3:1.0-port0
```

The tar contains `manifest.json`, `application.bin`, and `network.bin`, with
load addresses, sizes, and SHA-256 hashes checked before opening hardware.
Binary extraction is rejected when an envelope contains a controller. The
flasher saves the validated images alongside its logs, programs and verifies
the network core first, then programs and verifies the application core. It
preserves settings, Toit storage, and UICR. A failure stops the sequence; this
is not an atomic update and an interrupted update must be reflashed. Initial
debug protection may still require the separately documented recovery procedure.

Use the board's SWD flash tool for programming; `firmware flash`, OTA,
configuration extraction, and signing are not implemented for this kind.
This makes no commitment to a future OTA layout.

Hardware tests passed for both snapshot and precompiled-image inputs. Each
firmware ran a named application with 5003-byte assets, checked startup flags,
explicitly started a second named container, and completed the VM smoke test
with 1552 garbage collections. Both test images were 602,112 bytes (588 KiB);
the system-only image was 503,808 bytes (492 KiB). The entire persistent storage
partition was compared before and after these tests. See the test README for
reproduction and logs.

Further hardware qualification includes power consumption without an active
debugger, faster I2C with external pull-ups, and ADC accuracy against a calibrated
source. BLE pairing, callback lifetime, and repeated adapter teardown already
have tests described below; they do not qualify radio power consumption or
implement the unsupported BLE APIs listed above. OTA sizing and layout remain
deferred until the full image requirements are known.

## Network-core and Bluetooth preparation

The E83 board now has a `e83_2g4m03s_tb/nrf5340/cpunet` target for Zephyr's pinned
`samples/bluetooth/hci_ipc` controller. It uses the RC low-frequency clock and
does not claim console or fixture GPIOs. The controller builds to 129420 bytes
of its separate 256 KiB flash and 26120 bytes of its 64 KiB RAM. These are build
results. The controller now runs on this board: the native host probe passed
HCI initialization, AES-128 known answers, random generation, four simultaneous
advertising/scanning cycles, and shutdown/reopen. See
`build/nrf5340-ble/native-hardware.log`.

The opt-in application overlay `toolchains/zephyr/bluetooth.overlay` restores
the HCI IPC device and reserves the final 64 KiB of application SRAM for
OpenAMP. Its chosen application SRAM is 448 KiB, keeping libc and Toit heap
allocations out of the IPC region. `bluetooth.conf` enables the host with four
connection slots. Zephyr's HCI transport hooks start the network core on open
and force it off on close; boot-time network-core enable stays disabled to
avoid retaining an extra power reference. `hci-ipc.conf` selects the matching controller
connection count. The normal build remains independent of the network core.
The setup script fetches OpenAMP and libmetal at Zephyr's pinned revisions.

The default BLE build's external controller supplies LE Rand and LE Encrypt. The small
`bluetooth_crypto.c` adapter implements Zephyr's crypto wrappers over those HCI
commands, avoiding conflicting PSA/Mbed TLS libraries in the Toit VM link.
An opt-in shared PSA provider is available through `CONFIG_TOIT_PSA_CRYPTO`.
It uses the same vendored Mbed TLS 3.6 headers, configuration and library as
Toit, with sixteen volatile key slots and AES/CMAC/P-256 support. Zephyr's
own Mbed TLS library must remain disabled. The
[shared crypto qualification](../tests/hw/nrf5340/README.md#shared-bluetooth-and-toit-crypto-qualification)
exercises this provider with SMP self-tests and selected existing Toit crypto
regressions. Exhaustive pure-Toit Hamming and MD5 sweeps remain a separate,
optional program; the full board run was stopped in MD5 and is not a pass.
The focused board qualification passed the native PSA vectors, two Toit
crypto runs, sixteen adapter reopen cycles, and seventeen runs of the enabled
SMP self-tests (AES-CMAC, signing, f4/f5/f6/g2/h8), followed by VM teardown.
Evidence is in `build/nrf5340-security/summary.json` and
`focused-hardware.log`. The qualification image is 733184 bytes (716 KiB),
with 134820 bytes of static RAM; it includes test code and SMP debug logging.
OpenAMP reported non-empty virtqueues during teardown, which still completed.
The crypto qualification alone does not enable Toit's secure-connect API.
`settings.conf` supplies a dedicated NVS backend, and
`bluetooth-security.conf` enables central `connect --secure`, `bonded-peers`,
and peripheral `--bonding` / `--secure-connections`.
The adapter worker loads the `bt`
settings subtree after enabling the host and before reporting readiness,
including on reopen. These configurations remain opt-in. Secure central
connections require a bond. Incoming peripheral connections negotiate bonding
according to the peripheral's flags. Each role has its own authentication
callbacks; creating or closing a local peripheral must not change central-link
security policy.
The four-cycle role-isolation test passed with a security-disabled local
peripheral created before or after a secure central connection. Closing the
local peripheral preserved the central link and its encrypted GATT read
(`build/nrf5340-peripheral-security/mixed`).
The settings-enabled BLE build passed two full sixteen-cycle adapter tests,
then a dedicated sixteen-cycle test verified restoration of the stored GAP

its factory identity, so this setup does not require a `bt/id` record.
See `build/nrf5340-settings/ble/summary.json`. The dedicated qualification image

The separate `ble-pairing-nrf5340.toit` qualification uses an independent

See `build/nrf5340-pairing/positive` and `persisted` for both consoles.
Three attempts each also passed for peer refusal, missing bonding, and

Secure connect requires LE Secure Connections, a 128-bit encryption key,
and a bond before reporting success. This uses Just Works (security level 2),

not a durable-write acknowledgement for every connection.

lists the values most-significant byte first.
The native probe includes AES-128 known-answer checks in both byte orders,
48-byte random generation, and four advertising/scanning cycles. It builds at
124660 bytes. With the newly compiled PWM backend, the optional full VM build
with console DMA enabled links at 593920 bytes (580 KiB), with 123992 bytes of
static RAM and a maximum ATT MTU of 247. The normal image is 512000 bytes
(500 KiB), with 105576 bytes of
static RAM. The normal PWM-enabled build has passed the PWM hardware suites;
the PWM-enabled BLE build passed the full server suite at MTU 23 and 247 before
automatic exchange was enabled. Runtime MTU
preference changes remain unsupported. Automatic MTU exchange is now enabled

can still be 23 immediately after connection, before the exchange completes.

and `server-order23-console.log`). This exposed an ESP32 callback ordering bug:
NimBLE can report a peer-initiated MTU exchange before reporting CONNECT.
The ESP32 backend now remembers that event and publishes connection readiness

Previously the first service discovery could fail with ENOTCONN even though
Toit's connect call had returned successfully. Secure pairing is not qualified
by these unencrypted tests.
The updated ESP32 backend also passes the sixteen-connection MTU-247 suite
against `server-qualified.bin`, with nRF automatic exchange disabled. This

(`auto-mtu/server-order247-hardware.log`, `server-order247-console.log`).
The automatic-exchange build also passes the full connection lifecycle suite
against the independent Bluedroid fixture: 32 immediate connect/close cycles,
cancellation, timeout, adapter teardown and final VM teardown. The peer records
all 37 expected remote disconnects (`auto-mtu/connect-hardware.log`,
`connect-peer-console.log`).
The native probe and several full-VM BLE suites now pass on the board; the
remaining qualification gaps are listed below.

The first Toit BLE backend stage implements adapter ownership, asynchronous
initialization, active/passive scanning with deadlines and cancellation,
nonconnectable advertising with optional scan-response data, and cleanup.
One adapter may be owned at a time. Its central and peripheral managers share
that owner. Scan callbacks copy legacy reports into a fixed 16-entry queue;
they never retain HCI buffers or invoke the VM scheduler from the Bluetooth
RX thread. Overflow is reported as `QUOTA_EXCEEDED` instead of silently dropping
reports. A dedicated worker handles scan start, stop, and deadline waits.
Limited discovery filters advertisement flags. A zero-duration scan completes
without starting the controller scanner.

The shared BLE library recognizes `system.PLATFORM-ZEPHYR` and handles native
adapter-start and scan failures. Native resources are removed from the event
source before their workers are joined. Adapter close disables Bluetooth after
its managers close. If controller initialization or shutdown fails, the radio
core is forced off and another adapter cannot be opened until reboot.
Unencrypted central connections now support create, cancellation, disconnect,
and querying the negotiated ATT MTU. Native resources own Zephyr connection
references and callback lookup is protected against deletion. An early callback
can arrive before `bt_conn_le_create` returns; lookup uses the normalized peer
address during that interval. Teardown also handles a successful connection
racing with cancellation by disconnecting again. Explicit close and destruction
currently drain synchronously, with a five-second callback wait budget (HCI
commands have their own Zephyr timeout). This can pause the VM scheduler during
close; moving that drain to a worker remains desirable. A failed drain prevents
new connections/scans until reboot. The shared library releases cancelled
constructors immediately and tracks pending connections during manager close.
GATT service, characteristic and descriptor discovery now use separately owned
request objects. Closing the Toit resource detaches and cancels its request;
the callback parameters stay alive until Zephyr completes the request. Result
callbacks copy UUIDs, properties and handles into a bounded 64-entry buffer.
Overflow reports `QUOTA_EXCEEDED`. Native attributes are published only after
all result allocations succeed, and each holds its own connection reference.
Disconnect events are forwarded to every attribute on that connection.

Service/characteristic queries accept zero or one UUID filter. UUID comparison
normalizes 16/32/128-bit representations, while filtered results retain the
query's representation for Toit's result ordering. Characteristic discovery
always visits every declaration before filtering so descriptor ranges stop
before the next declaration. Empty descriptor ranges complete locally without
wrapping handle 65535. Handles and characteristic MTUs can be queried. The
shared library clears discovery failure events before retrying.

Zephyr's discovery callback does not expose ATT error codes; it reports a null
attribute both for completion and for ATT errors. Disconnect, malformed copied
records, and buffer overflow are detected, but other peer-side ATT discovery
errors can look like empty or partial results. Interrupted discovery, read and
write waits now invoke a Zephyr cancellation primitive, as does resource close.
Request cancellation races, allocation rollback and disconnect/close ordering
still require hardware qualification.

Characteristic and descriptor reads assemble Read/Read Blob fragments into a
native 512-byte buffer. Empty reads return an empty byte array. Writes support
Write Request (with response) and Write Command (without response), bounded by
ATT MTU minus three and the 512-byte attribute limit. Request data remains in a
native copy until its callback; command data is copied into Zephyr's TX buffer
before the call returns. ATT status codes are exposed as `Bluetooth ATT error
0xNN`; native errno failures remain OS errors. Reads clear stale failure flags
before retrying. Only one native GATT operation may be active per attribute.
The shared cancellation hook is appended to the BLE primitive table; other
backends retain their existing wait behavior and expose an unimplemented hook.
Cancellation detaches the resource from late callbacks and preserves parameter
memory until Zephyr completes. It does not roll back writes already applied by
the peer or guarantee that the next ATT request can run before the peer replies.

Notification and indication subscriptions now discover the characteristic's
CCC descriptor and write its value with a separate, owned request object.
Local notification routing uses `bt_gatt_resubscribe`; it does not share its
callback parameters with CCC writes. Local routes remain registered until
disconnect, with a maximum of 16 routes across all connections. Each route
allocates an eight-value queue with a 512-byte limit per value. Closed routes
can be reused on the same connection. These limits bound native memory use.

Notifications have separate storage and a separate readiness event from read
results. Empty values are preserved. Overflow clears the queue, reports
`QUOTA_EXCEEDED`, and schedules a best-effort CCC disable; oversized values
report `OUT_OF_RANGE`. Subscription cancellation and close stop local delivery,
detach late callbacks, and schedule CCC cleanup without blocking the Bluetooth
system work queue. Cleanup can be delayed by an outstanding ATT response and
is not a guarantee that the peer has stopped transmitting. Disconnect releases
local registration references. Reconnect does not automatically resubscribe.
Resubscribing clears the local queue, but cannot retract packets already queued
by the peer. After overflow, applications must resynchronize their stream.
The paired four-cycle notification/indication suite now passes, including
receiver cancellation, overflow recovery and active-subscription disconnect.
Further callback-race qualification remains. Runtime MTU configuration,
directed advertising, and extended advertising remain explicitly unimplemented.
Central secure connections are available with the opt-in security configuration
described above.

The local GATT server now supports dynamic primary services, characteristics,
descriptors, stored values up to 512 bytes, and incoming Write Requests/Commands.
16-bit UUIDs retain their width; 32-bit UUIDs expand to the Bluetooth base UUID
because ATT declarations carry only 16- or 128-bit UUIDs. CCC descriptors are
created and managed by the backend, with values validated against the declared
notification/indication properties. Read/write permissions are passed to
Zephyr. Encrypted-only characteristics and descriptors work with the opt-in
security configuration and peripheral pairing enabled. Their local read/write
methods accept the encrypted permission bits without adding plaintext access.

Incoming writes use an independent eight-entry queue per writable attribute.
They do not overwrite its stored read value. `LocalCharacteristic.read` or
`LocalDescriptor.read` consumes the next queued write, including empty writes.
On overflow the queue is cleared, the peer receives an insufficient-resources
error when its write requires a response, and the next Toit read reports
`QUOTA_EXCEEDED`. Write Commands cannot receive an ATT error response. Toit
can update the read value explicitly with `set-value`. Outgoing notifications
copy into host buffers; indications own their parameters and payload until
Zephyr's destroy callback after ACK, error or disconnect. At most eight native
indication requests can be outstanding, also subject to host ATT buffer limits.

A dedicated advertising worker handles HCI calls and restarts undirected
connectable advertising after connections. Exhausted connection slots defer
restart until Zephyr reports a recycled slot. Cancellation of the initial
advertising wait stops its worker operation. Stopping advertising preserves
established links; closing the peripheral drains its incoming links and
unregisters its services. Central-role links remain owned by the central manager.

Native service definitions outlive their Toit wrappers. Closing a wrapper
detaches it from callbacks, and retired definitions are retained until a
successful adapter shutdown aborts Zephyr's dedicated RX thread. This also
covers GATT accesses arriving over central-role connections. A limit of 64
local ATT entries includes both active and retired definitions; closing and
reopening a peripheral repeatedly within one adapter can reach that limit.
Closing the adapter reclaims those definitions. There are at most 16 services
per peripheral. A failed incoming-link drain or database unregister prevents
adapter reuse until reboot and retains any memory Zephyr may still reference.
